## Critical and high — the ones that touch a servo or lose work

### H1 — Bench: the link-row rate box and Finish disagree, and Finish streams positions at the old rate · Reproduced here

`hw-ui.js:135` `$('hwFreq').onchange = e=>{ serialSetFreq(+e.target.value|0); … }` → `serial-link.js:581-593`: `HW.setFreq(hz)` (the live setup), all-off, then the config frame — **but `HWCFG`, the "what did I last send the board" record in `hw-host.js:362`, is never updated**, and neither is `SETUP.hw`, the wizard's detached copy taken at `setupOpen()` (`setup-hw.js:192`). Finish → `setupApply()` (`:1409-1411`) → `HW.setSetup(Object.assign({}, SETUP.hw))` puts the OLD rate back, then `HW.applied()` → `hwCfgPush()` (`hw-host.js:382`) sees `HWCFG.freq === HW.freq()` (50 == 50), sends nothing, and `rebuild(true)` → `serialSyncAll()` → `serialTicksFor()` at 50 Hz.

Reproduced against the built dist with a fake bridge: box → 200 Hz (config frame `ch 63 = 200` sent, board now at 200 Hz); "drive a channel to wake it" → ch 0 streams `1229` ticks = 1500 µs, correct; **Finish → ch 0 queued at `307` ticks with no config frame in front of it** — on a 200 Hz prescaler that is **375 µs**; `HW.freq()` reads 50 afterwards; `setupClose()` then closes the port and leaves the horn there. Two bugs in one: the rate the user chose is silently reverted, and the last thing on the wire is a full-travel slam. Same shape as v1.75.0's two board counts that were never one number.

**Fix:** the two frame writers (`serialConfig`, `serialSetFreq`) own the last-sent record — move `HWCFG` into `serial-link.js` as `SER.sentFreq/sentOsc` and have both writers stamp it; and have the link-row box write `SETUP.hw.freq` too (or read the rate from `HW.setup()` at Finish rather than from the copy). **Test:** the sequence above; assert a config frame precedes any position frame whenever `HW.freq()` differs from the last rate written, and `SETUP.hw.freq === HW.freq()` after the box.

### H6 — An imported sketch that throws is persisted before it has ever run — the app is dead on every boot · Reproduced here

`sketch-import.js:964-980` (`readInoFile`): `sketchRegister()` stores the source (`sketchStore()`, `:908`) and only builds the closure; `buildSet('firmware', prof.id)` (`:971`) persists the answer and runs `setup()`; the identifier accounting deliberately ignores method names (`:674`), so a sketch calling any library method the adapter lacks transpiles residue-free and throws `TypeError` at run time. Reproduced with a six-line `.ino` calling `mp3.playFolder(1,2)`: the catch shows *"nothing was guessed"* (it was stored), `PREFS.build.firmware = 'sketch:bad'`; **after reload `SIM.ticks` never moves, `#btnTheme` is unbound, one `pageerror` per boot** — `main.js:378 loadProfile(bootFw)` throws synchronously inside the `load` handler and skips every line after it (button bindings, `initSelect`, `requestAnimationFrame(frame)`). The fallback at `:374` does not help: the profile IS registered, it just throws. A throw in `loop()` is the same shape one frame later: `fwLoop()` throws inside the fixed-step `while` and `acc` is never decremented, so every subsequent frame throws on its first step. **Fix:** trial-run `setup()` and a few `loop()` passes inside the `try` BEFORE `sketchStore()`/`buildSet()`; wrap `PROFILE.loop()` for `sketch:` profiles so a throw unloads the profile, falls back to `firmwareRecommend()` and names the method. **Test:** `sketch.test.js` — register a sketch whose `setup()` calls an unknown method; reload; assert `frame` runs and `SIM.profile !== sketch id`.

### H7 — A strings-only puppet take switches untouched servos OFF on a real Maestro · Reproduced here

`puppet.js:228-237` writes each keyframe as `new Array(MSTR.servoCount).fill(0)` with only the changed channels set (*"untouched channels stay 0 = leave it alone"*), and `:278` stores the list as `cat:'Recorded'`; the cued path densifies (`cues.js:287-297`), this one does not. The sim plays it correctly (`playback.js:150` reads 0 as untouched). **The board does not:** `export.js:46-56` emits a target whenever `now !== last` and `genFrameRow` pads the `.mstr` row the same way, and a Maestro target of 0 is *stop sending pulses*. Reproduced with `genSeqBody` on a three-frame take (ch 1 opens, then ch 2 opens):

```
  50 0 8000 0 0 frame_0..3   ← channels 0, 2, 3 commanded to 0: pulses off
  50 0 8000 frame_1_2        ← channel 1, opened 50 ms ago, commanded to 0: the panel goes limp
  900 0 frame_2
```

`lint.js:207 if(!t) return;` skips zeros, so nothing warns; `puppet.test.js:180` pins the sparse shape as a contract; `puppet.js:19-20, 291` send takes to "Put on the board". **Fix:** densify strings-only takes at `puppet.js:278` with the existing `cueDensify()` and carry every servo-mode channel; add a lint rule "non-zero → 0 mid-sequence = pulses off". **Test:** record a take that opens one channel and holds it; assert `genSeqBody` never emits a 0 for a channel that had a non-zero value in the previous frame.

### H8 — A nested library sequence compiles per-frame speeds above the channel's own limit · Reproduced here

`blocks.js:704-708` synthesises a speed for **every** interval, including those a `seq` brick commands, and `travel.js:53-56` never caps at `c.speed`. Reproduced: channel speed 120 / accel 100, a library routine with a 100 ms full-throw frame nested as one brick → compiled `speeds: 224` (1.9× the limit; with accel 0 it is 400). The act-brick path is floored by `blockMinTravelMs` (`:199-206`); the seq-brick path has no floor and no cap. It reaches hardware: `pca-gen.js:288-292` writes it under `MPCA_SEQ_SPEEDS`, `MaestroPCA.cpp:491-494` applies it over the table, `serial-link.js:644-645` sends it as Set Speed. The 3D preview ignores speeds, so the model shows the snap while the droid outruns its calibrated limit. The `roundtrip` fixture already nests `Dome Pie Wave` (110 ms frames) and writes speed 224 on speed-120 channels, unasserted. **Fix:** clamp in `chanSpeedForMs` to `c.speed` when set; emit no synthesised speed on an interval a `seq` brick commanded (carry the nested frame's own `speeds`). **Test:** `ramp-step.test.js` — for every compiled frame `!f.speeds[c.i] || f.speeds[c.i] <= (c.speed || Infinity)`.

### H9 — Re-importing your own `.mstr` binds subs to the wrong routine when two names share a symbol · Reviewer-confirmed

Export names the subs from the **loadout** (`export.js:137` `scriptSubNames(sequences)` with `sequences = load`, `:370`); import names them from the **whole `<Sequences>` list** (`import.js:275-277`). The `_2` suffix depends on order and membership, so they disagree whenever two names collapse onto one `niceName()`. Pure-function harness: library `['Dome Wave','Dome_Wave','Pies']`, loadout `['Dome_Wave','Dome Wave','Pies']` → script subs `Dome_Wave, Dome_Wave_2, Pies` → imported loadout `['Dome Wave','Dome_Wave','Pies']` — slots 0 and 1 swapped; `restartScript(0)` fires a different routine than before the save. The adopt-rename suffix `·` (`import.js:530`) produces the same collision in ordinary use. **Fix:** `genScript` already writes `# <seq.name>` above each `sub` (`export.js:139`); read that line back and match on the exact library name first, symbol second. **Test:** `roundtrip.test.js` — two colliding names, loadout in reverse library order, assert `MSTR.loadout` is identical after the trip.

### H10 — Every JSON door copies channel fields unvalidated; `NaN` disables every clamp · Reproduced here

`servo-cfg.js:194` `SERVO_CFG_READ_FIELDS.forEach(k=>{ if(r[k] !== undefined) c[k] = r[k]; })` — thirteen fields, no type or range check, on the servo config, whole-setup and choreography `.json` doors; `import.js:181-188` `parseInt` admits `NaN` from a `.mstr`; `servo-store.js:161` trusts the stored blob. Every clamp downstream is a comparison, and comparisons with `NaN` are `false`: reproduced with `min:'abc'` — `pcaSetTarget(E, ch, 16000)` → `target 16000, pos 16000`, and `hw-host.js:272-274` hands `st.target` to `serialMove`. With a quoted number (`min:"4000"`, the common hand-edit) `blockValueAt`'s `closed + …` concatenates and compiles targets of `40004000`. The 500–2500 band is enforced only in typed boxes (`setup-hw.js:1027-1031`); lint is comparison-based too. This is DATA-03's sim-side twin. **Fix:** one `chanNormalise(row)` (finite integers, `0 ≤ qus ≤ 16383`, mode from the enum, name a string) shared by `servoCfgApply`, `servoStoreLoad`, `setup-io.js:201` and after `mstrParse`. **Test:** import `{"channels":[{"i":0,"min":"abc","max":"4000"}]}` and assert every field is a finite number inside the hard band.

### H11 — The calibration dial cannot drive past the stored endpoints on the bridge/engine path · Reproduced here

`setup-hw-cal.js:211-214` says *"pcaSetTarget clamps at SET time and the step never re-clamps"*. It does: `pcaseq.js:459-462` clamps `pos256` into `c.min/c.max` every tick, and `calDrive()` (`:237-244`) restores the endpoints in its `finally` before the first tick. Reproduced: channel 1250–1750 µs, speed 40, driven once so it is active; dial to 1100 µs (4400 qus) → `target 4400` accepted, **position after 3 s = 5000** (the stored min). Only a never-driven channel snaps through (`!active && !known`, `:192`), so the FIRST turn works and the second does not — it reads as flaky. `hw.test.js:1236` and `setup-bench.test.js:191` test only the paced-Maestro path, and the latter asserts `.target`, not the position. Re-calibrating a narrowed channel over PCA_Bridge is therefore impossible. **Fix:** a per-channel `free` window on the engine (set by `calDrive`, cleared by `setupCalLeave/Commit/Cancel`) that `pcaStepChannel` clamps to instead. **Test:** `calSet(9600)`, tick 200, assert `HW.pos(ch) === 9600`.

### H12 — `HW.rebuild(true)` drops `known` · Reviewer-confirmed

`hw-host.js:212-213` carries `active, pos256, vel256, target, aim` — not `known`. ### H13 — A malformed Studio project file bricks Studio on every subsequent load · Reviewer-confirmed

## Medium

**M1 — Configure-panel speed/accel/sleep never reach the engine · Reproduced here.** `setup-hw-channels.js:975-978` writes `c[k]` and `HW.save()` — no rebuild, no `pcaSetSpeed`. Table 120 → 77: engine still 120. The "Move it now" slider (whose tooltip promises the engine's speed applies) moves at the old speed; on a paced Maestro `serialMove` reads `c.speed` live, so the **board ramps at the new speed while the model ramps at the old** — two views onto one thing disagreeing, which is this project's own definition of a bug report. `setup-bench.test.js:199-221` asserts `c.speed` only. **Fix:** route the four through `HW.changed()`.

**M2 — The wizard's Dome lighting answer never reaches the lights · Reproduced here.** `wizard.js:413-419, 528-532` call `buildSet('domeLights', …)`; `APX.on` is written only in `apxInit()` (`commands.js:423`), called from boot and the Model-pane tick (`lights/ui.js:67`). `buildSet('domeLights','teeces')` → answer `teeces`, `APX.on` still `true`; `apxInit()` by hand → `false`. The comment at `commands.js:406-407` describes a re-run that does not exist. The two doors that write one answer therefore disagree on screen. **Fix:** `apxInit()` from `buildApply()` when `domeLights` changes.

**M3 — AstroPixels rig lifecycle · By reading.** `render3d.js:414-418` `lrShowLegacy(!on); if(!on) return;` — nothing hides or unmounts `LR.rigs.*`, so turning the layer off leaves both rigs visible with their last texture, in front of the stand-in's legacy fittings (`DOME_R` vs `DOME_R*0.985`). `lrFitDome()` (`:239`) and `lrRig()` (`:390`) are never invalidated: `buildCad`'s swap disposes the rig's geometry with the old dome, then `lrMount()` (`:402-404`) re-parents the OLD rig with the OLD fit onto the new dome — `cad.test.js:359` already swaps to the Polar Mouse under the default build and gets MK4 logic panels floating over it, unasserted. `commands.js:440-444` tests `LR.built/rig/panels`, none of which exist on `LR`, so a `fldBoard` change would write 720 bytes into a 360-byte texture. **Fix:** one `lrReset()` (unmount, dispose, clear `tex/rigs/cadFit/host`) from `apxSetOption`, the CAD swap and `APX.on=false`.

**M4 — Jawalite accepted by non-MD sketches · By reading.** `commands.js:47-56` declares `jawa:false` on `standard`/`imperial`/`r2kt`; `jawa` is never read. `apxSend('@1T3')` on the Standard sketch passes to `apxJawa` and the logics go to ALARM — the false positive the module says it exists to prevent (`:21-25`); the command box's own placeholder offers `@1T3`. **Fix:** `if(/^[@:*]/.test(s) && !fw.jawa) return apxRefuse(…)`.

**M5 — `pcaseq.js` vs `MaestroPCA.cpp` · Reviewer-confirmed.** (a) `pcaseq.js:385` clamps a tick at 200 ms; `MaestroPCA.cpp:468` does not (widened in v1.69.0) — one 250 ms tick steps 20 in JS, 25 in the firmware (`bounds_test.cpp:108`); `hw-clock.js` caps at 250, so a throttled tab advances frames 250 ms and servos 200 ms per fire.
