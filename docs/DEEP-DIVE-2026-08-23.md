# R2D2 code, reliability, and novice-UX deep dive

**Reviewed:** 2026-08-23  
**Repository:** `D:\Projects\R2D2`  
**Source version:** 1.75.0  
**Review type:** current-state code audit, clean-build test pass, release-path audit, firmware host compilation, hostile-input probes, and first-time-user walkthrough

## Executive summary

R2D2 is unusually thoughtful about physical safety, destructive imports, firmware fidelity, offline distribution, and regression testing. The current code has strong guardrails around servo travel, board identity, configuration replacement, imported choreography, and hardware disconnects. The simulator also contains far more user guidance than most specialist tools.

It is not ready to release as 1.75.0 yet.

The most important current issues are:

1. **User-controlled and imported names can execute JavaScript in both the main simulator and PCA Studio.** This was reproduced, not inferred. In a tab with a connected board, injected code runs in the same context as the hardware controls.
2. **A clean 1.75.0 build has a red browser-test baseline.** Five assertions fail in each main deliverable: two around the foot-controller warning, one around the sequencer's “more below” claim, and two around header information disappearing at a wide desktop size.
3. **The release workflow builds `Esp32Droid.zip` but does not attach it**, while the README advertises the missing release asset.
4. **The main generated files can be stale without the test entry point detecting that fact.** The reviewed working copy contained 1.74.1 deliverables beside 1.75.0 source; running current tests against them produced missing-global crashes.
5. **The advertised developer commands do not work from a normal Windows shell.** Both `npm test` and `npm run build` fail before doing any work.
6. **“The whole setup in one file” is not actually portable for custom firmware or the sound bank.** The import path now warns safely, but only after the user discovers their backup is incomplete on the second machine.
7. **The novice journey remains too long and too structurally ambiguous.** A first run is 15 wizard stops, the shipped defaults knowingly contain two firmware conflicts, and Setup / Configure / Board / Build & files divide related tasks in ways a newcomer cannot predict.

My recommendation is to treat findings **SEC-01, TEST-01, REL-01, and BUILD-01 as release blockers**. The UX work can then be delivered in two passes: make the first successful drive and first successful sequence short and obvious; then simplify the project's file/export and hardware-setup vocabulary.

## Scope and method

The review covered the authored simulator, PCA Studio, build and release tooling, tests, Arduino library/sketches, manuals, and current design/handover material. Generated embedded payloads and vendored libraries were treated as build inputs rather than hand-audited line by line.

The following checks were performed:

- Mapped the source manifest, shared global dependencies, persistence boundaries, import/export paths, hardware seams, and release workflows.
- Built fresh 1.75.0 versions of `dev.html` and `R2D2-Simulator.html`, tested both, then restored the original ignored files byte-for-byte.
- Ran all 37 main browser suites against both fresh deliverables: **6,106 assertions passed and 10 failed**—the same five failures on each target.
- Ran PCA Studio's smoke suite: **86 passed, 0 failed**, with no page errors; its tracked build is current.
- Compiled and ran the native MaestroPCA protocol, engine, multi-board, ESP32-core, sketch, and three bench-backend sections. Those sections passed. The final ZIP-packaging step could not run locally because WSL had no `zip` command; the test's documentation names only `g++` and the Pololu library as prerequisites.
- Reproduced code execution through a renamed Model Builder part and through a PCA Studio sequence name.
- Tested the documented Windows `npm` commands; both fail at shell dispatch.
- Walked the information architecture and novice path using the current source, current Playwright layout tests, and the repository's captured screens. The in-app browser would not open a local `file://` URL under its security policy, so no claim below depends on a fresh interactive browser capture.

The repository already contains detailed reviews from 2026-08-22. This report does not re-list items that current code and tests show as fixed; it concentrates on what remains or has changed since then.

## Detailed technical findings

### SEC-01 — user and imported names execute code

**Evidence**

- `src/js/core/util.js:90-92` builds section headings with `innerHTML` from both `title` and `right`.
- `src/js/cad/ui.js:356` passes `mbPartLabel(rec)` as that raw `right` value.
- `src/js/scene/builder.js:866-870` accepts a typed name, only limiting it to 40 characters; it does not make the value safe for HTML.
- `pca-studio/src/js/40-ui.js:14` concatenates `s.name` directly into `innerHTML`.
- The PCA project and `.mstr` imports accept names from local files, so the input does not have to be typed in the app.

Two probes were run against the current built apps:

```text
Model Builder name: <img src=x onerror="window.__x=1">       executed = 1
PCA sequence name:  <img src=x onerror="window.__pcaInjected=1">  executed = 1
```

This is not only a cosmetic markup bug. The injected script can read and change the whole in-memory project. If the user has already granted serial access, it shares the page context that can send servo commands.

**Fix**

- Make `sect()` create text nodes and a `span` with `textContent`. If a caller genuinely needs markup, give that path an explicitly named, tightly controlled API.
- Replace PCA Studio's string-built tabs and tables with DOM nodes or escape every imported/name field at the final sink.
- Audit every `innerHTML` assignment using this rule: constants may use markup; any value that came from a prompt, file, filename, model, profile, channel, sequence, or user preference must be text.
- Add regression tests using event-handler attributes, not only `<script>` tags; scripts inserted with `innerHTML` often do not execute, while event handlers do.
- Do not rely on a Content Security Policy as the primary fix. This single-file app intentionally uses inline scripts, and the unsafe DOM construction still corrupts layout even if code execution is later restricted.

### TEST-01 — fresh 1.75.0 fails its current behavioral contract

A source-fresh build was tested against both `R2D2-Simulator.html` and `dev.html`. The same five assertions failed on both.

#### TEST-01a — the foot-controller explanation loses to an older toast

`tests/build-config.test.js:3062-3080` expects an attempted drive with “Not decided yet” to produce a plate naming the missing foot controller and to make that plate the way back to question 7. The screen instead exposes the unrelated older message:

```text
Channels 24-47 are yours to name now
```

The expected clickable plate cannot be found, so the return path is `null`.

The underlying gate in `src/js/config/hardware.js:860-902` is sensible. The failure shows that message ordering/stacking can hide the one explanation needed at the moment the droid refuses to move. A novice experiences this as “the controls do nothing and the app talks about channels.”

**Fix:** give cause-of-refusal messages a dedicated status area or priority channel, rather than competing with informational receipts in a generic toast stack. Test both the message and its action with a pre-existing toast present.

#### TEST-01b — the sequencer says READY-MADE is below when it is visible

At 1440×900, the brick library is clipped and there is more content below, but the READY-MADE heading is already visible. The footer still says:

> more below — READY-MADE builds a whole figure in one click

`tests/sequencer-ui.test.js:1863-1872` records `clipped:true`, `rmBelow:false`, `hasMore:true`.

**Fix:** compute the label from what is actually below. If READY-MADE is visible, say simply “more below,” or name the next hidden group. The action should scroll to the first hidden content, not a hard-coded category.

#### TEST-01c — wide desktop header still sheds important status

At 1520×950 the body settles on `hdrshort`, hiding the version and replacing full chip labels, even though the 1.75 design contract says only the new Build & files word should be shed at that size. See `tests/chrome.test.js:93-107`, `src/js/app/main.js:265-295`, and `src/css/02-layout.css:65-75`.

The current body class was:

```text
seqv-blocks light ws-config hdrshort
```

**Fix:** measure the whole header cluster, not just whether individual chip children clip after layout. Give the workspace switcher and action buttons explicit flex priorities, keep the Drive state readable, and add screenshot coverage at 1280, 1440, 1520, 1920, and 150% UI scale.

### REL-01 — the release omits Esp32Droid

The three relevant sources disagree:

- `README.md:21` links to `releases/latest/download/Esp32Droid.zip`.
- `arduino/packs/make-packs.sh:39-41` builds `R2_Bench_Console`, `MaestroReplacement`, and `Esp32Droid`.
- `.github/workflows/release.yml:72-74` attaches only the first two ZIPs.

The release body at `.github/workflows/release.yml:86-87` also names only two packs.

**Impact:** the prominent README download for the new ESP32 route will not be produced by the automated release. The pack may compile perfectly in CI and still be unavailable to users.

**Fix:** attach the third ZIP, name all three in the release body, and add a release-manifest check that compares the pack builder's declared outputs with the workflow's attachment list. That prevents the next pack from being forgotten in the same way.

### BUILD-01 — the main artifacts can be stale without a failing guard

At the start of this review:

- `src/js/core/util.js:10` was 1.75.0.
- The ignored `R2D2-Simulator.html:4031` was 1.74.1.
- `dev.html` referenced current source, but its body/manifest shell was an older generated copy.

Running current tests against the stale main files produced failures including missing 1.75 globals such as `WIZ_ADV`. A fresh build removed those missing-symbol failures and exposed the five real current failures above.

`test.sh:61-70` verifies only the tracked PCA Studio build. There is no equivalent in-memory comparison for either main generated file. CI builds immediately before testing, which keeps CI useful but also masks the missing guard in local and packaging workflows.

**Fix**

- Add a `tools/check-build.js` equivalent to `tools/check-studio.js` for both main targets.
- Make `npm test` either build to a temporary directory or refuse stale targets before running suites.
- Record the source version/build fingerprint in generated files and assert it in the harness before the first suite.
- Keep the generated files ignored; the problem is not that they are untracked, but that a user can open or test a stale one with no unmistakable warning.

### UX-01 — a fresh setup starts in a state known to conflict

`tests/build-config.test.js:75-100` deliberately pins the current behavior: the shipped answers use one controller with two expanders and a DY-SV5W, while the default `mod2026` firmware drives neither. A new build therefore contains exactly two objections before the user has caused any.

There is even an internal documentation contradiction:

- `src/js/config/hardware.js:335-338` says a fresh user opens with zero conflicts.
- `src/js/config/hardware.js:344-348` and the tests explain that the two conflicts are intentional.

This was an explicit product choice, not an accidental code regression. It is still hostile to onboarding: the first review teaches the user that defaults are not a runnable recommendation, while another part of the source calls them a clean slate.

**Options**

1. Make the default a genuinely coherent simulation-first starter and offer Mike's common hardware as a named preset.
2. Keep the hardware defaults, but let the setup choose the compatible firmware before the first review.
3. If the mismatch must remain, present it as a single up-front decision: “Your hardware preset needs Maestro 2025; switch now?” Do not make the novice interpret two independent conflict cards.

### DATA-01 — the “whole setup” promise is incomplete

The setup export is substantial and useful. `src/js/app/setup-io.js:18-58` includes firmware ID and constants, preferences, models, tracks, build answers, RC calibration, Maestro channels/sequences/loadout, and CAD mapping.

It does not include:

- The source of a custom imported `.ino`; that source is stored separately in localStorage by `src/js/profiles/sketch-import.js:914-918`.
- The sound bank; audio files live in IndexedDB.

The file's header calls itself the “portable, complete version,” `src/js/app/panels.js:535` labels the area “one file, everything,” and the export toast says “the whole setup in one file.” Yet `tests/setup.test.js:179-233` proves that a custom-profile setup on another machine must be repaired by importing the `.ino` first.

The import behavior is now safe—it refuses to merge constants onto the wrong firmware and tells the user what to do. The UX defect is that the backup's limitation is revealed only during recovery.

**Fix**

- Short term: rename it **Setup snapshot** and list “Does not include: sound files; imported sketch source” beside every export button and in the receipt.
- Better: add an optional **Portable project bundle** ZIP containing setup JSON, custom sketches, a sound-bank manifest, and optionally the audio files. Keep the small JSON for routine snapshots.
- On export, produce a coverage receipt: configuration ✓, choreography ✓, custom sketch ✓/missing, sound bank included/not included.

### TOOL-01 — the documented npm entry points fail on Windows

`package.json:7-9` delegates directly to `./build.sh` and `./test.sh`. From PowerShell/npm on Windows both commands fail with:

```text
'.' is not recognized as an internal or external command
```

The underlying Node builder works on Windows, and the browser suites also work when invoked with Windows-compatible orchestration. The failure is only the public entry point a contributor is told to use.

**Fix:** move orchestration into Node scripts and let the shell files be thin Unix wrappers. For example, `npm run build` should call a Node build orchestrator, and `npm test` a Node suite runner. This also removes duplicated shell logic and makes the same commands work in CI, PowerShell, cmd, and Git Bash.

### DATA-02 — autosave failures can be invisible

- Main preferences: `src/js/look/prefs.js:35-36` catches every `localStorage.setItem` failure and says nothing.
- PCA Studio: `pca-studio/src/js/30-project.js:22` also swallows the failure.
- Model Builder contains a good local workaround at `src/js/scene/builder.js:587-597`: it reads the save back and warns once.
- Custom sketch storage logs a warning at `src/js/profiles/sketch-import.js:914-918`.

The inconsistency means the most complex user-created objects receive mixed guarantees. A full quota, private-mode restriction, or blocked file-origin storage can leave parts of a session durable and other parts temporary.

**Fix:** make persistence return a result, maintain one always-visible save state (`Saved`, `Saving`, `Not saved—export now`), and reuse the Model Builder's read-back verification for all important stores. PCA Studio should prominently suggest a project-file download when autosave is unavailable.

### DATA-03 — PCA Studio project import is under-validated

`pca-studio/src/js/40-ui.js:136-153` checks only for the existence of `channels` and `sequences` before assigning `PROJ = p`. It does not validate:

- array and object shapes;
- channel/sequence/frame caps;
- numeric bounds and finite values;
- target-array widths;
- generator records;
- schema version;
- dangerous strings before they reach HTML sinks.

The current app's own exports are well formed, but hand-edited, older, foreign, or malicious files can take down rendering or amplify SEC-01.

**Fix:** add a versioned validator/normalizer that builds a new safe project object before replacing the current one. Cap sizes before rendering, report dropped records, and preserve the current project if nothing usable remains—the same strong pattern already used by the main Model Builder import.

### ARCH-01 — global script order is a deep future-risk seam

The main app loads more than 100 classic scripts into one shared global scope. `src/manifest.json` is effectively a dependency graph written as a list. `tools/build.js:37-59` correctly catches source files missing from the manifest, but it cannot express or validate which module provides each global.

Symptoms of the architectural pressure are visible in the source:

- Modules rely on globals declared in many unrelated folders.
- A duplicate top-level name can break the whole app at parse time.
- `src/js/scene/builder.js:1464-1472` needs `try/catch` because `typeof` cannot safely probe a later uninitialized lexical binding.
- Dev and distributable parity requires delicate script-tag behavior.

This architecture made rapid single-file development possible, and a wholesale rewrite would be risky. The right move is incremental containment.

**Fix sequence**

1. Create namespaces for new work (`R2.config`, `R2.sequence`, `R2.hw`) instead of new top-level names.
2. Give each legacy subsystem one explicit public object and migrate consumers toward it.
3. Generate or validate manifest dependency metadata.
4. Move pure modules to ES-module build inputs while continuing to emit a self-contained classic-script deliverable.
5. Keep the existing end-to-end suites as the migration safety net.

### REL-02 — version and release metadata are not one contract

Current values disagree:

- App source: 1.75.0 (`src/js/core/util.js:10`).
- `package.json` and `package-lock.json`: 1.44.1.
- Restored local main deliverable: 1.74.1.
- README size: approximately 7.7 MB; a fresh current build reported approximately 8.76 MB.
- Release workflow comments also still say 7.7 MB.

`package.json:4` additionally sets `private:false`, with empty homepage and repository URL fields. This makes an accidental `npm publish` possible while publishing stale metadata.

The release workflow has no visible assertion that a `vX.Y.Z` tag, `APP_VERSION`, package metadata, manual copy, and generated artifact agree.

**Fix:** keep one machine-readable version source, update all consumers during build/release, assert tag parity, set `private:true` unless npm publication is intentional, and remove facts such as generated file size from hand-maintained prose.

### DOC-01 and TOOL-02 — small drift that should be automated

- The current manual and app say **21 chapters and 8 clips** (`src/js/app/manual.js:270`).
- `.github/workflows/release.yml:80-82` still says 20 chapters and 7 clips.
- README contains current and older counts in different places.
- Build/release/test comments repeatedly call the firmware output “two packs” even though the builder now declares three.
- `arduino/MaestroPCA/test/run.sh:2-4` says it needs `g++` and the Pololu library, but the final test also requires `zip` and `unzip`. On this machine all native sections passed and the run stopped only when `zip` was not found.

**Fix:** calculate manual counts in its builder, generate release snippets or check their constants, compare declared packs to attached packs, and add a prerequisite check at the start of the native script.

## Novice-user walkthrough

### 1. “Which thing do I download?”

The top of the README presents the simulator, manual, PCA Studio, and three hardware packs. That is useful for an experienced builder, but a newcomer does not yet know whether PCA Studio is part of the simulator, a replacement for it, or firmware. One advertised pack is not attached by the release workflow.

**Improve:** lead with one primary choice—**Start with the simulator**—then branch into “I only want to calibrate servos” and “I am ready to flash hardware.” Put the specialist artifacts under those goals.

### 2. “I opened it; why am I answering 15 pages?”

`wizSteps()` is one model choice, eight hardware questions, then Servo bench, Wiring, Panels, Colours, Scene, and Finish: **15 stops**. Much of the language is necessarily specialist: Mega ADK, UART, I2C, PCA9685, co-processor, firmware families, addresses, board arrangements.

The pictures and explanations are strong, and some questions offer “None yet,” “Not decided yet,” or “Something else.” That escape is inconsistent; the code itself notes at `src/js/maestro/ui-pane.js:106-110` that the servo question has no not-yet answer.

**Improve:** split onboarding into two modes:

- **Try the simulator**—model, controls, a coherent virtual hardware preset, then Drive. Three steps maximum.
- **Match my real build**—the full hardware interview, available immediately or later from Setup.

Every hardware question should offer “I do not know yet—keep this virtual,” with a visible confidence/status summary rather than a forced guess.

### 3. “The droid does not move.”

The app correctly boots feet disarmed and has added cause-specific explanations. This is a safety strength. The current failing test shows the explanation can lose to an unrelated toast, leaving a newcomer with a non-moving droid and a message about channels.

**Improve:** reserve a persistent **Why it is not moving** line beside the Drive state. It should report exactly one current blocker in order: overlay open, no foot controller, feet disarmed, controller not connected, puppet/mouse owns input, or hardware link issue. A button should perform or navigate to the remedy.

### 4. “Where do I change something?”

The header currently contains four workspaces plus three overlapping utility doors:

- Drive
- Sequence
- Configure
- Board
- Setup
- Build & files
- Menu

The internal distinctions are logical to the code:

- Setup asks what is built.
- Configure edits the model and sketch settings.
- Board handles Maestro/PCA work.
- Build & files guides build/import/export/assign jobs.
- Menu contains setup-file save/load and preferences.

A novice cannot infer those boundaries. “Setup,” “Configure,” and “Build” are near-synonyms; “Board” contains servo configuration and sequence deployment; “Build & files” is a task wizard, not a place.

**Improve:** organize the visible top level around outcomes:

1. **Drive**
2. **Make a sequence**
3. **My droid**—hardware, model, wiring, colours
4. **Put it on hardware**—connect, calibrate, import/export/deploy

Keep preferences and backup in a clearly labelled menu. Contextual “continue” buttons can route into the same underlying panes without exposing every seam in the top bar.

### 5. “I want panels to open, the dome to turn, and a sound to play.”

The sequencer is powerful, but its mental model is layered:

- a sequence in the library;
- bricks and generated frames;
- a board loadout;
- subroutine/slot numbers;
- pad cues or music-track triggers;
- a file format chosen by hardware family.

The handover still lists a sound lane and dome rotation in the sequencer as open work (`HANDOVER.md:477-485`). Current music support explains that the user must fire the sound cue and the servo subroutine together on the droid (`src/js/maestro/music-ui.js:110`). That is technically honest, but it is not the creative task the user thinks they are building.

**Improve:** make a show timeline the primary concept: servo actions, dome rotation, and sound cues aligned on one time ruler. Compilation may still emit separate board artifacts, but export should present them as one deployment plan and say what must be triggered together.

For the existing model, use one sentence consistently:

- **Library** = routines saved on this computer.
- **On the board** = the numbered routines the controller can call.
- **Slot** = the number used by the sketch.

Show all three in one board-loadout screen and avoid switching between “sub,” “script,” “sequence,” and “routine” unless the underlying file format genuinely requires it.

### 6. “I connected real hardware—am I safe?”

This is one of the product's strongest areas. The code is explicit about:

- drive arming;
- live-servo arming and disarming;
- board identity before streaming;
- pulse limits and endpoint warnings;
- turning pulses off;
- no V+ wiring claims;
- port ownership;
- replacement confirmations and save-a-copy gates;
- board-specific pacing.

The remaining friction is density. The bench presents calibration, mapping, streaming, serial, firmware output, and file conversion in one broad domain. New users need the safe guided path first; experts need the dense table.

**Improve:** default to a four-step bench checklist—Connect, identify one channel, set safe travel, save/deploy—with the full table and serial monitor behind Expert. Keep the current panic stop always visible.

### 7. “I saved everything; why is it missing on the other laptop?”

The setup export sounds complete but omits custom firmware source and sounds. Other legitimate exports include model-only JSON, servo-only JSON, choreography JSON, `.mstr`, `sequences.h`, `servos.h`, and full setup JSON. The app has made major progress in explaining each one locally, but the overall taxonomy is still hard to remember.

**Improve:** every export choice should answer three questions in one row:

| File | Contains | Use it with |
|---|---|---|
| Setup snapshot | App configuration, model, mappings, choreography | This simulator |
| Portable project | Snapshot + custom sketches + optional sounds | Another computer/builder |
| Servo calibration | Channel names and measured travel | Simulator/PCA Studio |
| Board program | Numbered routines compiled for the chosen board | Arduino IDE or Maestro Control Center |

Prefer goal labels on buttons (“Move this project to another PC,” “Put these routines on my board”) and leave extensions as supporting text.

### 8. “Did it save?”

Several stores autosave with no durable-state indicator. A user cannot distinguish “saved locally,” “only in memory,” and “downloaded as a portable file.”

**Improve:** add one quiet global state indicator and use the same words everywhere:

- **Saved in this browser**
- **Not saved—browser storage is blocked**
- **Portable copy exported 13:42**

Do not use “saved” for both localStorage and a downloaded file without the location.

## Duplication and confusion hotspots

### User-facing duplication

1. **Setup vs Configure vs Build & files**—three doors that all sound like changing the droid.
2. **Servo configuration in multiple contexts**—Setup step, Board pane, Outputs, the bench overlay, PCA Studio, and file import wizard. Much of the engine is shared, but the user repeatedly has to decide which entrance is appropriate.
3. **Outputs in Drive and Board**—intentional and useful, but the same pane should visibly say “Also shown in Board” so it reads as one tool, not two tables.
4. **Sequence library vs board loadout vs sketch slot map**—three representations of related data with multiple names.
5. **Many save/export surfaces**—individually well explained, collectively hard to classify.
6. **Live manual vs release manual vs in-app fallback**—technically resilient, but counts and copy have drifted among them.

### Code and documentation duplication

1. **Classic global host seams** are duplicated between the main simulator and PCA Studio. The shared engine and hardware table are a good direction, but PCA's `40-ui.js` still owns a separate string-built view and import shell.
2. **Firmware library copies** live beside multiple sketches. This is intentional for Arduino usability and is protected by byte-for-byte tests; keep the guard and generate/sync the copies from one source.
3. **Historical reasoning lives in several places**—large source comments, HANDOVER, tests, README, and dated reviews. The detail is valuable, but it now contradicts itself in places such as default conflict count and pack count.
4. **Facts that can be counted are hand-written**—manual chapters/clips, pack quantity, generated file size, version numbers.

**Improvement principle:** retain comments that state an invariant and why it matters; move release history and prior failed approaches into focused ADRs or the handover. Generate count/version facts. This reduces the chance that the most confident paragraph near the code is no longer true.

## Recommended delivery plan

### Phase 0 — release blockers

1. Fix all unsafe HTML sinks and add hostile-name tests in both apps.
2. Fix the five current main-app assertions and require a completely green fresh build.
3. Attach `Esp32Droid.zip`; verify workflow attachments from the pack manifest.
4. Add main-build freshness checks and a source/artifact version assertion.
5. Decide whether the default setup is coherent or explicitly a named hardware preset; remove the contradictory zero-conflict claim.

**Exit condition:** fresh build, 75 suite runs green, hostile names render literally, expected release artifacts enumerated and present.

### Phase 1 — protect user work and make Windows first-class

1. Replace shell-only npm entry points with cross-platform Node orchestration.
2. Add visible persistence state and warnings for every important store.
3. Rename the current export to Setup snapshot and disclose exclusions.
4. Design the optional portable project bundle.
5. Add strict PCA project validation and caps.
6. Make package/version/tag metadata one checked source of truth.

### Phase 2 — shorten the novice path

1. Add a three-step simulation-first onboarding path.
2. Make “I do not know yet—keep it virtual” available for every hardware question.
3. Add the persistent cause-of-no-motion status/action.
4. Consolidate navigation into outcome-based areas.
5. Put safe guided bench steps before the expert table.
6. Add first-success telemetry locally—not analytics, simply checklist state: drove, opened a panel, made a sequence, exported a backup.

### Phase 3 — deepen the creative workflow and architecture

1. Add sound and dome-rotation lanes to the sequencer/deployment model.
2. Unify library/loadout/slot presentation.
3. Introduce subsystem namespaces and explicit dependency metadata.
4. Move pure logic toward modules while preserving the one-file deliverable.

## What is already strong and should be preserved

- The simulator models known firmware behavior—including bugs—instead of silently “improving” the simulation.
- Hardware writes are gated by board identity, capability, arming, endpoints, and explicit user actions.
- Imports increasingly preserve current work, offer a copy, and refuse partial lies.
- The single-file offline distribution is excellent for a workshop laptop.
- Main and PCA logic already share important engine and hardware seams.
- The regression suite is broad and unusually rich in real user history. The current red run is useful evidence that it can catch experience regressions.
- Firmware host tests cover protocol bytes, bounds, multiple boards, both ESP32 core families, and copied sketch libraries.
- The interface contains many precise explanations and escape routes. The next UX gain comes from reducing when those explanations are needed, not from adding more prose.

## Final assessment

R2D2 has a strong engineering core and an unusually serious approach to real-hardware safety. Its main weakness is not lack of capability; it is that capability has accumulated faster than the product's top-level mental model and release integrity checks.

Fix the executable-name injection and return the clean build to green first. Then make one coherent route for each of the four things a user actually wants to do: **drive a virtual droid, match a real build, create a show, and put that show on hardware**. If every screen and file operation clearly belongs to one of those outcomes, much of today's friction and duplicated explanation disappears without removing the expert power underneath.
